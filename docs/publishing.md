# 发布到 GitHub / jsDelivr

应用通过可更新的索引发现新版解析源，再下载固定版本的 JS 文件。先发布 JS，确认可访问后再发布索引。

## 发布前准备

- 准备公开的 GitHub 仓库，并确认索引分支名称，下面以 `main` 为例。
- 按 [README](../README.md#本地开发) 构建并检查，在 Flutter 宿主中验证解析结果。
- 提交源码及生成的 `dist/`、`test/fixtures/`，确保待发布版本内容完整。

下面的 `OWNER/REPO`、`v1.0.0`、`main` 均需替换为实际仓库、版本和分支。

## 首次发布

1. 将包含构建产物的提交推送到 GitHub，为该提交创建并推送 tag，例如 `v1.0.0`。
2. 确认固定版本的 JS 可以访问，例如：

   ```text
   https://cdn.jsdelivr.net/gh/OWNER/REPO@v1.0.0/dist/xhs.js
   ```

3. 在与该 tag 内容一致的本地代码根目录生成发布索引：

   ```sh
   npm run publish:index -- --repo OWNER/REPO --ref v1.0.0
   ```

4. 将生成的根目录 `index.json` 提交并推送到索引分支 `main`。
5. 确认索引及其中引用的 JS 均可访问，再将索引地址配置给应用：

   ```text
   https://cdn.jsdelivr.net/gh/OWNER/REPO@main/index.json
   ```

发布工具只生成本地文件，不会推送代码或创建 tag。它会检查本地 JS 与构建索引的摘要是否一致，但不会检查远端 tag 内容。生成索引时，本地 `dist/` 必须与 `--ref` 指向的文件一致，否则应用下载后会因摘要不匹配而拒绝安装。

## 两种索引

| 文件 | 生成方式 | 用途 |
| --- | --- | --- |
| `dist/index.json` | `npm run build:sources` | JS 地址为相对路径，用于构建检查和宿主内置源同步 |
| 根 `index.json` | `npm run publish:index` | JS 地址固定到 tag 或完整提交号，用于远程更新 |

索引的 `apiVersion` 当前为 `1`，每个源包含 `id`、`version`、`url`、`sha256`。摘要由工具计算，不要手工填写。

`--ref` 接受 `v1.0.0` 形式的版本 tag（可带后缀），或 40 位小写十六进制提交号，不接受分支名。可通过 `--out path/to/index.json` 指定输出位置；应用的索引地址也需相应调整。

## 发布更新

1. 修改受影响的平台，并递增其 `manifest.json` 中的 `version`，例如从 `1.0.0` 改为 `1.0.1`。
2. 重新构建、检查并在宿主中测试，然后提交并推送生成文件。
3. 发布新的固定 tag，例如 `v1.0.1`，确认 JS 已可访问。
4. 使用新的 `--ref` 生成根索引，将索引提交并推送到 `main`。
5. 检查线上索引版本和 JS 内容，并在应用中执行一次检查更新。

仓库 tag 标识整次发布，平台 `version` 标识单个解析源的版本，两者不必全部相同。只递增 tag 而不递增平台版本，客户端不会识别为该平台的新版；修改公共模块影响多个平台时，应递增所有需要分发更新的平台版本。

当前源 API 为 `1`，普通平台修复保持 `apiVersion` 不变。接口协议调整需要同步宿主支持，不能仅通过修改此字段发布。

不要覆盖已发布 tag。jsDelivr 的索引缓存可能延迟新版可见时间，应以线上实际返回的索引为准。应用校验源 ID、版本、SHA-256 和模块加载结果；单个平台更新失败时保留旧版。SHA-256 用于完整性校验，不是发布者签名。

## 同步 Flutter 内置版本

远程更新不修改 Flutter 包内置的源文件。如需让后续发布的应用直接携带新版解析源，在宿主仓库执行 `tool/sync_sources.dart` 并运行回归测试，具体命令见 [README](../README.md#本地开发)。
